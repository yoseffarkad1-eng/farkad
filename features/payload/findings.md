# What this app costs to install, measured

Measured on the integration branch at the commit named in the report that cites this
file. Every number below came from a command printed beside it; nothing is estimated.

## The offline shell

    2,527,812 bytes across 46 files          the whole precached shell
    1,634,730 bytes across 44 files          without the vendored library
      881,727 bytes                          vendor/xlsx-0.18.5.min.js alone
      489,026 bytes                          own code, concatenated and gzip -9

The service worker precaches all 46 files on install, so this is paid **once per build**,
over whatever signal the phone has at that moment, and never again for the life of that
build. After that the app opens from cache with no network at all — which is the point,
and is why the number is a one-time cost rather than a per-open one.

The three biggest own-code files, raw and gzipped:

      146,967 → 41,780   css/app.css
      136,905 → 41,918   js/ui/reports.js
      130,341 → 40,475   js/sync/sync.js

`index.html` is 35,859 → 10,855.

## 55.8% of the shipped JavaScript is prose

Counting every line of the 36 own JS files in the shell — a line is a comment if it opens
`//` or lies inside a `/* … */`:

    1,328,640 bytes total
      585,153 bytes  code      44.0%
      741,256 bytes  comment   55.8%
        2,267 bytes  blank      0.2%

**This is not a defect and the recommendation is to leave it alone.** `CLAUDE.md` says
every comment in this codebase names the failure the code below it prevents, and reading
the source bears that out: the comments are where the reasons live, and most of them
record a bug that actually happened. Deleting them to save bytes would be trading the
thing that makes this codebase maintainable for a download nobody waits through twice.

It is written down because it is a real number the owner has never been shown, and
because two plausible-sounding future changes are settled by it:

- **"Minify the shipped JavaScript."** It would remove roughly 741KB raw — but gzip
  already collapses prose hard (the whole of own-code compresses 1,634,730 → 489,026,
  about 3.3:1), so the saving over the wire is a fraction of that, and it costs a **build
  step**. `CLAUDE.md` opens by saying there is no build step and that `package.json`
  "exists so the tests can be run, not to introduce one". A build step also puts
  generated bytes between a person and their data, which the architecture section
  explicitly refuses. Not worth it.
- **"The app is too big, split it and load screens on demand."** The shell is precached
  precisely so that a man on a site with no signal gets the whole app. Lazy-loading a
  screen means a screen that fails to open in a tunnel. The one file that IS loaded on
  demand — the spreadsheet library — already has a CSV fallback and a sentence telling
  the person what happened, and that is the pattern to copy if anything else is ever
  deferred.

## What is NOT measured here

- **Real install time on a real phone over a real connection.** Nothing in this container
  can produce that number. `tests/update.test.mjs` deploys against a real service worker
  and proves the install is atomic, not that it is fast.
- **Runtime cost**, which is a different question with its own suite and its own findings
  (`features/performance/`). Bytes on disk and milliseconds on screen do not predict each
  other: the largest file here, `css/app.css`, costs nothing per render, and the fault the
  performance work found was one small function called 81 times.
